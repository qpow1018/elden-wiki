# 공통 코드 규약

프론트엔드와 백엔드 코드에 공통으로 적용한다. 기존 기준의 적용 범위는 새 코드와 요청 관련 수정이며, 기준 통일만을 위한 무관한 일괄 수정은 하지 않는다.

## Import·타입·이름 규칙

### Import

- 같은 폴더 또는 하위 경로의 `./` 상대 import는 허용한다. `../` 등 상위 경로로 이동하는 상대 import는 사용하지 않고 `src/*`를 가리키는 `@/*` 별칭을 사용한다.
- import는 외부 라이브러리 → 내부 로직 → UI 컴포넌트 → 스타일 → 아이콘·이미지 등 시각 리소스 순으로 배치한다.
- 그룹 사이는 빈 줄 하나로 구분하고, 없는 그룹은 생략한다.
- 경로보다 가져오는 대상의 역할로 분류한다. 외부 라이브러리에서 가져오더라도 UI 컴포넌트는 UI 그룹에, 아이콘은 시각 리소스 그룹에 둔다. 외부 라이브러리 그룹에는 React·Next.js API와 일반 라이브러리를 둔다.
- 타입 import는 관련 대상과 같은 그룹에 둔다. 같은 모듈에서 별도 선언이 필요한 import는 인접하게 배치한다.
- 타입으로만 사용하는 대상에는 `type`을 명시한다. 같은 모듈에서 값과 타입을 함께 가져오면 인라인 `type`으로 합친다. 예: `import { fetchItems, type TItem } from '@/lib/items';`.
- 타입만 가져오는 선언은 `import type`을 사용한다. 예: `import type { TItem } from '@/types/item';`.

### TypeScript

- 객체, union, 함수 등 새로운 타입은 기본적으로 `type`으로 선언한다.
- 새로 만드는 타입 이름에는 `T` 접두사를 붙인다. API 요청 타입은 `TReq`, 응답 타입은 `TRes` 접두사를 사용한다. 예: `TItem`, `TReqGetItems`, `TResGetItems`.
- 상수 데이터의 리터럴 값이나 읽기 전용 타입을 보존해야 할 때 `as const`를 사용한다.
- 모듈 수준에 선언한 고정 데이터 상수는 `UPPER_SNAKE_CASE`로 작성한다.
- 타입을 알 수 없는 값은 `any` 대신 `unknown`으로 받고, 사용 전에 명시적인 타입 검사로 타입을 좁힌다.

### 이름 규칙

- 직접 정의하는 boolean은 의미에 따라 상태는 `is...`, 존재·소유는 `has...`, 가능 여부는 `can...`으로 이름을 짓는다. 외부 라이브러리나 HTML API가 정한 이름은 이 규칙에 맞추려고 변경하지 않는다.
- 일반 조회·계산·변환 함수에는 역할에 맞는 동사를 사용한다.
- 긴 조건식은 의미 있는 boolean 이름으로 의도를 드러낸다. 이름 규칙을 맞추기 위해 단순 인라인 콜백을 기계적으로 분리하지 않는다.

## 함수와 가독성

- 이름 있는 일반 함수와 헬퍼는 함수 선언식으로 작성한다. 직접 전달하는 인라인 콜백은 화살표 함수로 작성하고, 기존 함수를 전달할 때는 불필요한 콜백으로 감싸지 않는다.
- 함수는 처리할 수 없거나 처리할 필요가 없는 조건을 먼저 반환해 중첩을 줄인다. 단순한 분기까지 기계적으로 조기 반환으로 바꾸지 않는다.
- 코드 줄 수보다 동작과 데이터 흐름의 가독성을 우선한다. 함수 분리 여부는 고정된 줄 수가 아니라 책임을 기준으로 판단한다.
- 파일 배치 순서나 함수 선언 형식을 맞추기 위해 함수의 책임·스코프를 변경하지 않는다.
- 여러 필드의 반환 객체와 긴 조건식을 한 줄로 압축하지 않는다.

## 포맷

- 프로젝트에 설치된 Prettier와 루트 `.prettierrc.json`을 사용한다. 포맷 옵션은 설정 파일을 기준으로 하며 이 문서에 중복 정의하지 않는다.
- 코드 작성·수정 후 변경한 코드 파일만 포맷하고, 같은 파일을 대상으로 `prettier --check`를 실행한다. 요청과 무관한 파일까지 일괄 포맷하지 않는다.
- import 그룹과 순서는 이 스킬의 Import 기준에 따라 별도로 유지한다.
