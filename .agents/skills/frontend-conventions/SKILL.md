# 프론트엔드 규약

사용자가 직접 코드를 보며 정한 기준을 보존하고 이후 프론트엔드 작업에 적용한다.

프론트엔드 코드 작업에는 [공통 코드 규약](../code-conventions/SKILL.md)을 함께 적용한다. API 구현·계약·오류 전파는 [백엔드 기준](../backend-conventions/SKILL.md)에서 관리하며, 해당 책임을 수정할 때 적용한다.

## 기준 관리와 적용 범위

- 사용자가 지적한 프론트엔드 코드 작성 기준은 별도의 스킬 수정 요청 없이 이 파일에 반영한다. 이유와 적용 범위를 보존하고 특정 사례를 근거 없이 일반화하지 않는다.
- 폴더·책임·의존 방향은 [아키텍처 문서](../../../docs/ARCHITECTURE.md), 공통 작업·협의·보고 절차는 [AGENTS.md](../../../AGENTS.md)를 따른다. 기준 기록만으로 제품 코드 변경 권한을 부여받은 것으로 해석하지 않는다.

## 코드 기준

### 파일과 컴포넌트 구조

#### 구조 기준

- 새 파일 배치·공통화·이동·책임 변경에는 [아키텍처 문서](../../../docs/ARCHITECTURE.md)의 구조·배치 항목을, API·Query·UI 연결 변경에는 의존 방향을 확인한다. 단순 표현·스타일 수정에 문서 전체 확인을 요구하지 않는다.
- 데이터 의미에 영향을 주는 표시·계산·필터 변경은 [DB 문서](../../../docs/DATABASE.md)의 관련 값·제약을 확인한다. 이 스킬은 구체적인 작성 방식과 공통화 판단 절차를 관리한다.
- App Router의 `page.tsx`는 서버 컴포넌트로 유지하고 `'use client'`를 선언하지 않는다.
- 대응하는 클라이언트 컴포넌트가 필요하면 페이지 의미에 맞는 `<PageName>Client.tsx`로 선언하고 `'use client'`를 적용한다. `page.tsx`에서 가져와 렌더링한다.
- 페이지의 복잡한 조회 로직은 별도 함수로 분리하고 페이지에서는 이를 호출해 결과를 전달한다.

#### 파일명과 폴더명

- 컴포넌트 파일명은 컴포넌트 이름과 동일한 PascalCase를 사용한다. `page.tsx`, `layout.tsx` 등 Next.js 예약 파일명은 예외로 한다.
- 일반 코드 폴더명은 소문자로 시작하는 camelCase를 사용한다. 예: `equipment`, `equipmentCard`.
- URL 경로를 만드는 정적 라우트 폴더명은 소문자 kebab-case를 사용한다. 예: `equipment-list`. Next.js의 동적 세그먼트·라우트 그룹·private 폴더 등 특수 폴더 문법은 유지한다.

#### 공유 컴포넌트와 공통 UI

- 라우트 전용 컴포넌트의 공유가 필요해지면, 공유할 이유와 사용할 라우트를 설명하고 배치 위치를 사용자에게 제안한다. 여러 라우트에서 쓴다는 이유만으로 자동으로 공통화하거나 이동하지 않는다.
- 새로운 공통화나 이동 시 아키텍처 문서의 공유 컴포넌트 배치 기준을 후보로 제안하고 사용자가 동의한 뒤 진행한다.
- 이 제안 절차는 새로운 공통화나 공유 위치로의 이동에 적용한다. 기존 공통 UI의 재사용에는 별도 동의를 요구하지 않는다.
- 새 UI 프리미티브를 만들기 전에 `src/components/common/`의 기존 컴포넌트를 확인한다.
- 공용 컴포넌트의 내부 스타일은 해당 컴포넌트가 관리한다.

#### 공통 로직

- React 훅은 `use...` 이름으로 구분하고 훅 호출 규칙을 지킨다.

### 서버 상태와 API

#### Query 객체와 조회 훅

- Query 파일은 도메인 이름의 객체를 default export한다. 예: `equipmentQuery`.
- 조회 훅은 객체 내부에 `use...` 메서드 문법으로 선언한다. 소비 컴포넌트에서는 `useQuery`와 옵션을 직접 조합하는 대신 `equipmentQuery.useGetEquipment()`처럼 호출한다. 호출 시 React 훅 규칙을 지킨다.
- Query 메서드는 API 함수를 연결하고 TanStack Query 결과를 그대로 반환한다.
- 한 메서드에서만 쓰는 옵션은 `useQuery`에 직접 작성한다. 별도 옵션 상수나 `queryOptions`는 재사용 필요가 있을 때 도입한다.
- 조회 옵션은 필요한 것만 명시한다. 라이브러리·프로젝트 기본값을 변경할 때는 실제 요구에 근거하며, 특정 옵션을 일괄 금지하지 않는다.

#### UI 타입

- API 타입으로 충분하면 그대로 사용한다. UI의 데이터 형태나 제약이 달라질 때만 별도 타입을 정의하며, 별도의 UI 타입 계층을 의무적으로 만들지 않는다.

#### 캐시와 상태 관리

- 조회 결과를 바꾸는 요청 조건은 query key에 포함한다. 화면에서만 사용하는 상태는 포함하지 않는다.
- mutation 성공 후 영향을 받는 캐시를 무효화하거나 정확한 응답 데이터로 갱신한다.
- Query의 서버 데이터를 별도 컴포넌트 상태에 장기 복제하지 않는다. 검색·선택 상태와 편집 초안은 목적에 따라 분리한다.

### 함수·훅과 렌더링

#### 대표 컴포넌트와 파일 내부 순서

- 파일의 대표 컴포넌트는 `export default function ComponentName()` 형태로 선언한다.
- 파일은 import → 모듈 수준 타입·상수 → 대표 컴포넌트 → 보조 함수·지역 컴포넌트 순으로 배치한다. 대표 컴포넌트를 먼저 읽고 세부 구현으로 내려가는 흐름을 유지한다.

#### 함수와 콜백

- 이벤트 props는 `on...`, 이름 있는 이벤트 처리 함수는 `handle...`을 사용한다.

- 대표·지역 컴포넌트는 함수 선언식으로 작성한다. Query 객체 내부의 훅은 앞의 Query 객체 기준에 따라 메서드 문법으로 선언한다.
- 훅을 포함해 직접 전달하는 인라인 콜백과 effect의 정리 콜백은 화살표 함수로 작성한다. 단순 계산이나 JSX 반환은 간결하게 표현한다.
- 컴포넌트에서 조기 반환할 때는 Hooks 호출 순서와 공통 페이지 구조를 유지한다.

#### 훅

- 훅 콜백의 동작을 한눈에 이해하기 어려우면 복잡한 작업을 콜백 내부의 이름 있는 함수로 분리해 호출한다. 콜백 자체를 `function synchronizeItems() { ... }` 같은 이름 있는 함수 표현식으로 바꾸는 것으로 대체하지 않는다. 하나의 작업에 필요한 검증·오류 처리를 기계적으로 나누거나 단순한 한 줄 계산까지 분리하지 않는다.
- `useCallback`으로 참조를 유지하는 함수는 반환값을 변수에 할당하는 형태를 허용한다. 예: `const handleReset = useCallback(() => { ... }, [])`.
- `useMemo`는 성능상 필요할 때 사용한다. 데이터를 보관하거나 조회 시점을 제어할 목적으로 사용하지 않는다.

#### 가독성과 조건부 UI

- JSX의 중첩 삼항연산자를 피한다. 공통 페이지 구조는 유지하고 조건부 영역은 우선 JSX 안에서 독립 조건으로 나누되, 동시에 표시되면 안 되는 상태는 조건이 겹치지 않게 작성한다. 단순 값 선택의 삼항연산자는 허용한다.
- 지역 컴포넌트 분리는 코드 길이보다 읽는 흐름을 기준으로 판단한다. 오류·빈 상태 같은 보조 UI가 주요 동작을 읽는 데 방해되면 짧아도 같은 파일 아래로 분리할 수 있다.
- 부모에는 표시 조건과 주요 데이터 흐름을 남긴다. 단순 분기를 위한 렌더 함수를 미리 만들지는 않는다.

### 스타일과 레이아웃

#### SCSS Modules

- 컴포넌트 스타일은 `*.module.scss`로 작성한다.
- 스타일 파일은 사용하는 컴포넌트와 기본 이름·대소문자를 맞추고 같은 폴더에 둔다. 예: `HomeClient.tsx` → `HomeClient.module.scss`.
- SCSS Module은 `styles`라는 이름으로 import한다.
- 클래스명은 kebab-case로 작성하고, `styles['class-name']` 형식으로 접근한다.
- 하위 요소는 대표 root class 아래에 nesting하되, HTML 계층을 그대로 복제하지 않고 요소의 관계가 읽히도록 작성한다.
- 상태와 modifier는 해당 요소 아래에 nesting한다.
- nesting 깊이는 고정하지 않고 HTML 구조와 가독성에 따라 결정하되, 불필요한 nesting은 피한다.
- `@keyframes`, `@mixin` 등은 사용 범위와 가독성에 맞춰 배치한다. 전역 스타일은 컴포넌트 스타일과 구분해 관리한다.

#### 전역 스타일과 Sass 공통 자원

- `src/assets/reset.scss`는 브라우저 기본 여백·박스·미디어·테이블·폼 초기화를 관리한다. 색상·서체·본문 줄 간격은 전역 스타일에서, 개별 UI 표현은 컴포넌트에서 관리한다. 전역 reset에서 포커스 표시·폼 기본 동작·링크와 목록의 의미를 일괄 제거하지 않는다.
- `_variables.scss`와 `_mixins.scss`는 전역 주입하므로 SCSS Module마다 `@use`를 반복하지 않는다.
- `line-height`는 `src/assets/global.scss`의 `body`에서 관리하며, 컴포넌트·라우트 스타일에서는 재정의하지 않는다.

#### 레이아웃

- 좁은 화면과 긴 텍스트에서도 콘텐츠가 의도치 않게 잘리거나 페이지 전체에 가로 스크롤이 생기지 않도록 작성한다.
- fixed 요소가 있다면 콘텐츠 가림 여부와 모바일 safe area·가상 키보드 영향을 확인한다.
