# 아키텍처

이 문서는 프로젝트의 기본 원칙, 폴더 구조와 역할, 영역 간 의존 방향을 관리한다. 구체적인 코드 작성 규칙은 [공통 코드](../.agents/skills/code-conventions/SKILL.md)·[프론트엔드](../.agents/skills/frontend-conventions/SKILL.md)·[백엔드](../.agents/skills/backend-conventions/SKILL.md) 스킬에서 관리한다. DB 모델은 [DATABASE.md](DATABASE.md)를 참고한다.

## 기본 원칙

- 코드는 책임과 사용 범위를 기준으로 배치한다. 라우트 전용 코드와 여러 라우트에서 공유하는 코드를 구분한다.
- 화면, 서버 상태 관리, 데이터 접근의 책임을 분리한다. 클라이언트에서 사용하는 서버 상태의 캐시·재조회는 TanStack Query, 화면의 검색·선택·편집 초안은 UI가 관리한다.
- 폴더 구조는 배치 기준이며 미리 만들어야 할 목록이 아니다. 필요한 코드가 생길 때 폴더를 만든다.
- 현재 구현과 합의한 배치 기준을 구분한다. 개별 기능의 구현 세부와 일시적인 설정값은 이 문서에 나열하지 않는다.

## 폴더 구조

현재 존재하는 주요 구조다. `<domain>`은 도메인별 폴더를 뜻하며 현재는 `equipment`가 있다.

```text
src/
  app/                      # 라우트·레이아웃·라우트 전용 화면
  api/
    index.ts                # 공통 API 연결·요청 처리
    <domain>/
      index.ts              # 도메인 API
      types.ts              # API 요청·응답과 관련 타입
      <domain>Query.ts      # Query 정의
  providers/                # 앱 전역 Provider
  components/common/        # 도메인과 무관한 공용 UI
  utils/                    # 공유 범용 함수와 React 훅
  lib/
    supabase/               # DB 생성 타입 등 Supabase 연동 기반
  assets/                   # 폰트·전역 스타일·Sass 공통 자원
public/                     # 정적 공개 파일
supabase/                   # 로컬 설정·마이그레이션·시드
docs/                      # 구조·데이터 모델 등 프로젝트 문서
```

### 필요할 때 추가하는 구조

다음은 기존에 합의한 배치 기준이다. 필요한 역할과 사용 범위에 맞춰 추가한다.

```text
src/
  app/<route>/
    _component/             # 라우트 전용 컴포넌트
    _type/                  # 라우트 내 여러 파일이 공유하는 타입
    _util/                  # 라우트 내 여러 파일이 공유하는 유틸
    _define/                # 라우트 내 여러 파일이 공유하는 상수
  components/
    <domain>/               # 여러 라우트가 공유하는 도메인 컴포넌트
    common/                 # 도메인과 무관한 공통 UI
  utils/                    # 공유 범용 함수와 React 훅
```

## 폴더별 역할과 배치 기준

### 라우트와 UI

- `src/app/`은 URL에 대응하는 페이지와 레이아웃, 라우트 전용 코드를 관리한다.
- `page.tsx`는 서버 입력 해석·필요한 서버 조회·라우트 조립을 맡는다. 대응하는 클라이언트 화면이 필요하면 `<PageName>Client.tsx`를 같은 라우트 폴더 바로 아래에 나란히 둔다. 두 파일은 `_component/`로 옮기지 않는다.
- 분리한 라우트 전용 컴포넌트는 `_component/`에 둔다. 여러 파일에서 공유하는 라우트 전용 타입·유틸·상수는 `_type/`·`_util/`·`_define/`에 둔다.
- 한 파일에서만 쓰는 타입·유틸·상수는 기본적으로 해당 파일에 둔다. 독립된 책임이 있고 분리하는 편이 읽기 좋으면 추출할 수 있다. 컴포넌트마다 폴더를 만들거나 종류만으로 기계적으로 분리하지 않는다.
- 공유 도메인 컴포넌트는 `src/components/<domain>/`, 도메인과 무관한 공통 UI는 `src/components/common/`에 둔다. 새로운 공통화·이동 시의 제안과 동의 절차는 프론트엔드 스킬을 따른다.
- UI 전용 타입은 사용하는 코드 가까이에 두며, API 폴더에 모으지 않는다.

### 서버 상태와 데이터 접근

- `src/api/index.ts`는 공통 API 연결과 요청 처리를 담당한다.
- `src/api/<domain>/index.ts`는 도메인 요청 실행과 응답 변환, `types.ts`는 API 계약과 관련 데이터 타입을 담당한다. UI에서도 사용한다는 이유로 API 타입을 복제하지 않는다.
- `<domain>Query.ts`는 도메인 API를 호출하고 Query 키·캐시·재조회 정책을 담당한다. API와 같은 도메인 폴더에 두되 책임을 분리한다.
- 로딩·오류·빈 상태 표시, 안내·토스트·페이지 이동은 UI의 책임이다.

### 공통 기반과 자원

- `src/providers/`는 전역 Context와 라이브러리 Provider를 조립한다.
- `src/lib/`는 외부 서비스·라이브러리 연동 기반을 둔다. 현재 `supabase/`에는 DB 생성 타입이 있다. 도메인 데이터 접근은 `src/api/`에서 관리한다.
- `src/utils/`는 여러 곳에서 쓰는 범용 일반 함수와 React 훅을 함께 관리한다. 훅이라는 이유로 별도 `src/hooks/`를 만들지 않으며, API·Query나 라우트 전용 코드를 이곳에 모으지 않는다.
- `src/assets/`는 코드에서 사용하는 폰트와 전역 스타일·Sass 공통 자원, `public/`은 공개 URL로 제공하는 정적 파일을 관리한다.
- `supabase/`는 DB 로컬 설정·스키마 변경 이력·시드, `docs/`는 구조·정책·선택 이유를 관리한다.

## 의존 방향

```text
클라이언트 UI → Query → 도메인 API → 공통 API 연결 → 데이터 서비스
서버 컴포넌트 → 도메인 API → 공통 API 연결 → 데이터 서비스
```

- API는 React·Query·UI에 의존하지 않는다. Query는 도메인 API를 호출하며 UI 처리를 수행하지 않는다.
- UI는 DB 테이블이나 외부 데이터 서비스를 직접 호출하지 않고 도메인 API를 통해 접근한다.
- 서버 컴포넌트 조회나 캐시 관리가 필요 없는 단발성 요청은 도메인 API를 직접 호출할 수 있다. 서버 조회의 도입 여부는 기능 요구에 따라 판단한다.
- 현재 공개 데이터 조회는 Supabase를 사용한다. 브라우저 코드를 보안 경계로 간주하지 않는다.

## 구조 변경 기준

- 새 코드는 기존 책임과 사용 범위에 맞는 위치를 먼저 찾는다. 새 계층·공유 폴더는 실제 필요가 있을 때 도입한다.
- 기존 구조의 역할 설명과 현재 요구에 필요한지에 대한 평가를 구분한다. 기존에 있다는 사실만으로 유지 필요성을 정당화하지 않으며, 제거·재배치는 요청 범위 안에서 판단한다.
- 구조를 합의하거나 변경하면 이 문서의 관련 내용을 갱신한다. 작성 방식의 변경은 해당 스킬에 기록하고, 동일한 배치 규칙을 양쪽에 중복 관리하지 않는다.
- 이 문서는 전체 구조를 다루며 개별 기능의 Query 키·캐시 시간·화면 동작·DB 컬럼은 각각의 코드와 관련 문서에서 확인한다.
